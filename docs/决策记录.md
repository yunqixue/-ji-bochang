# 决策记录（ADR）

> 记录「为什么这么选」，避免两周后三个人都忘了原因又重新吵一遍。
> 只记**会影响多人或难以回退**的决定，小事不用写。

## 写这个文件的规则（2026-10-23 修订，起因：一次真实冲突）

1. **只追加，不改别人写的条目。** 发现别人写错了 → 在群里说，由本人改。
2. **改之前必须先 `pull`。** 不 pull 就写，几乎一定撞车。
3. **新条目追加到文件末尾**（不是最上面）。
   > 原来规定"最新的在最上面"，结果两个人同时往顶部插，git 无法自动合并，直接冲突。
   > 末尾追加虽然也可能撞，但只在"同一天两人同时写 ADR"时才会发生，概率低得多。
4. **一次只一个人写。** 三个人同一天都有决定时，商量一下谁先写，另一个等对方推完再写。
5. 写之前先看一眼文件末尾，确认最新的 ADR 编号，接着往下编。

## ADR-010 · 演示链分四级兜底，优先级：能演 > 好听 > 聪明

> 编号说明：本条原写作 ADR-009，与 C 的「效价/唤醒度交给模型直接判断」撞号（C 提交时间更早），2026-10-23 由 B 改为 ADR-010。

- **日期**：2026-10-23
- **背景**：把整条演示链跑通后统计出真实的脆弱点：LLM 需要联网、TTS 连微软服务器在国内 10 次失败 2 次、本机没有中文离线语音包。
  一旦现场网络出问题，原来的行为是"退回固定模板（每个情绪一句固定台词）"，观众立刻看出是死板的东西——比报错更尴尬。
- **候选方案**：
  1. 只保证联网时能演，断网就认了
  2. 四级兜底：真实模型 → 预置问答缓存（真实回复+已合成音频）→ 多变体模板（关键词嵌位）→ 纯文字
- **决定**：方案 2。
- **理由**：演示的失败代价是不对称的——"平淡但完整"远好过"聪明但中断"。
  预置缓存让断网时的回复和联网时**听不出差别**（同一句话、同一段音频），代价只是要提前跑一次预演。
- **代价 / 遗留**：缓存是精确匹配（做了标点/空格归一化），**只对预演过的台词有效**，演示时临时改词会掉到模板层；
  `data/demo_cache.json` 不进仓库，每台演示机要自己跑一次 `prewarm_demo`。
- **何时重新评估**：换成稳定的商用 TTS + 本地小模型后，兜底层级可以简化。

## ADR-005 · 演示统一跑在 B 的机器上

- **日期**：2026-10-23
- **背景**：三台机器的 Python 版本不一致——A/B 是 3.10，C 是 3.14.7。C 的机器上 `uvicorn[standard]` 和 `faster-whisper` 都装不上（ADR-003），而语音识别必须跑在服务所在的那台机器上。
- **候选方案**：
  1. 三台机器都统一到 Python 3.10，谁都能起服务
  2. 演示固定跑在 B 的机器上，C 只负责静态页面文件
- **决定**：选方案 2。
- **理由**：三天内让三台机器环境完全一致成本太高；而前端页面本来就是纯静态文件，不需要 C 本机跑服务。"服务只有一台、其余人只改文件"是更省事的形态。
- **代价 / 遗留**：**单点风险**——演示机就是 B 的电脑，它出问题整个演示停摆。缓解：D3 把整机彩排 + 录屏 2 份兜底。
- **何时重新评估**：如果要让外人远程访问（C 的内网穿透任务），届时跑服务的那台就是"服务器"，这条自动成立。

## ADR-004 · 实时 TTS 少重试、演示预演多重试

- **日期**：2026-10-23
- **背景**：实测边缘情况——`edge-tts` 连微软 `speech.platform.bing.com` 在国内每次尝试成功率约 40%。如果实时对话也用 3~8 次重试，一旦网络不好，一轮对话会被拖到 **18 秒**（实测数据），演示现场不可接受。
- **候选方案**：
  1. 实时对话保持高重试次数，保证有声音
  2. 实时对话只重试 2 次，失败立刻落 Windows SAPI 离线兜底；预演时才用 8 次
- **决定**：选方案 2（`synthesize(retries=)` 参数区分两种场景）。
- **理由**：**用户等待时间的优先级高于音质**。宁可这一句用稍差的 SAPI 音色，也不能让人干等 18 秒。预演不赶时间，慢慢补到全成功。
- **代价 / 遗留**：网络差时部分回复会用 SAPI（音色差一截）；`sapi` 兜底在受限账户下可能不可用（"当前安全设置下没有可用语音"）。
- **何时重新评估**：如果换上稳定的 TTS 服务（如云端商用 TTS），重试策略可以简化。

## ADR-006 · 外网演示用 cloudflared 临时隧道，链接不写进仓库

> 编号说明：本条原写作 ADR-004（与 B 的「实时 TTS 重试策略」撞号），2026-10-23 由 B 改为 ADR-006。

- **日期**：2026-10-23
- **背景**：任务板 D2 17:00 要「队友和外人可访问的链接」，本机一个穿透工具都没装。
- **候选方案**：
  1. cloudflared quick tunnel（免注册，一条命令出 https）
  2. ngrok（要 authtoken）/ cpolar、花生壳（要账号，国内可用性好）
  3. 退化为本机 `localhost` 演示
- **决定**：用方案 1 先打通；**链接只口头/对话里发，不写进仓库、不写进文档**。

## ADR-007 · ASR 模型自管自下，不用 huggingface_hub 的缓存

- **日期**：2026-10-23
- **背景**：接通 faster-whisper 时连撞三个坑：
  ① 默认缓存目录 `C:\Users\<用户>\.cache\huggingface` 在受限账户下直接 `WinError 5` 拒绝访问；
  ② huggingface_hub 下载模型时反复卡住（几分钟才 2.5MB），无法判断是在下还是死了；
  ③ 中途断流留下的残片文件"看起来存在"（vocabulary.txt 被截到正好 256KB），
     后续报错却是 `The current model is English-only` / `token was not found in the prompt`，
     排查方向被带偏很久。
- **候选方案**：
  1. 继续用 faster-whisper 自带的 HF 下载，只改 `HF_HOME` 到项目目录
  2. 自己写下载器：urllib 直连 hf-mirror，校验 Content-Length，重试，落到 `data/models/faster-whisper-<尺寸>/`，
     代码优先加载本地目录
- **决定**：选方案 2（工具在 `experiments/download_asr_model.py`）。
- **理由**：模型 150~500MB、只在演示前准备一次，值得用最笨但可控的方式。
  长度校验是这次的关键——没有它，截断文件会伪装成"另一个完全不相关的错误"。
  本地目录还让"队友之间拷一个文件夹"成为可行的共享方式。
- **代价 / 遗留**：模型不进仓库，每台需要语音输入的机器要自己跑一次下载脚本（约 2 分钟）；
  `ASR_MODEL_SIZE` 改变后要下对应尺寸的模型。
- **何时重新评估**：如果换成云端 ASR（讯飞/阿里云），这套完全不需要了。

## ADR-008 · 通话视图用「本地自拍预览」，不做画面理解

- **日期**：2026-10-23
- **背景**：需求从「聊天框」扩到「视频通话 / 语音通话」，用户明确要「真要摄像头画面」。同时评估过 DSH 生态的四个插件（dsh-galgame / dsh-chat-avatar / dsh-plugin-quick-chat / dsh-web-ui），结论是**它们都注册在 DSH 自己的 GUI 里，装不进我们这个独立 FastAPI 页面**，只能抄设计范式。
- **候选方案**：
  1. 真 WebRTC + 视觉模型，让 AI 看懂画面
  2. 浏览器 `getUserMedia` 本地自拍预览 + 通话式界面（立绘为主、自拍小窗、通话控制条）
  3. 不做通话，只保留文字
- **决定**：选方案 2。设计参考 `dsh-galgame` 的立绘舞台 / 差分淡入 / 说话弹跳。
- **理由**：方案 1 三天内不可能（要视觉模型 + 实时推理 + 上传帧），演示现场网络也不稳；方案 2 能给出「视频通话」的完整体验感，而且摄像头画面**不出本机、不上传、不送模型**，隐私上更干净，也省掉带宽。
- **代价 / 遗留**：**她看不到你的画面**——所谓"视频通话"只有通话感和自拍预览，界面上要如实标注，别让演示时产生误解。摄像头需要 HTTPS 或 localhost 才会被浏览器授权（临时隧道是 https，可用）。无摄像头 / 被拒绝时降级为「摄像头未开」，通话界面照常。
- **何时重新评估**：要做画面理解时，需引入视觉模型 + 帧采样上送，属于下一阶段，不在三天范围内。

## ADR-009 · 效价/唤醒度交给模型直接判断，不再用后端映射表

- **日期**：2026-10-23
- **背景**：用户要求「正确读取用户的感受」。此前 `valence/arousal` 是后端按情绪标签查一张写死的映射表（sad 恒为 −0.6、happy 恒为 +0.7 等），模型只输出情绪标签，读不出同一情绪下的强度差异。
- **候选方案**：
  1. 维持映射表
  2. 让模型在 JSON 里直接输出 `valence` / `arousal`，后端只 clamp + 兜底
- **决定**：选方案 2。
- **理由**：「有点难过」和「崩溃了」不该都是 −0.6；模型本来就在生成 JSON，多两个数字成本为零，却能给更细的数值。
- **代价 / 遗留**：mock / 断网兜底仍走映射表（此时没有模型值可用）；模型给的数值要做 clamp 防越界。改动落在 B 的 `agent.py`，属用户直接要求，已登记。
- **何时重新评估**：若发现模型数值不稳定（同一句波动大），可对 valence/arousal 做滑动平滑，或退回映射表。

## ADR-011 · 表情加「情绪余温」：这几句没情绪时不要立刻变回平静脸

- **日期**：2026-10-24
- **背景**：按真实演示节奏跑 9 句时发现，演示 3 第 3 句「你还记得我说过什么吗」被判成 `neutral`，
  于是智能体的表情从 `empathic` 切回平静脸 —— 内容上是对的（这句话本身确实没情绪），
  但**观众看到的是"她刚才还在共情，一问就变回冷脸"**，正好打在最能体现共情的那一幕上。
- **候选方案**：
  1. 不改：情绪判定正确，表情跟着判定走
  2. 让 A 改话术/改脚本，避开这类中性句
  3. 加「情绪余温」规则：前 3 轮里对方说过难过/焦虑/生气，本句判成 `neutral` 时表情仍保持 `empathic`
- **决定**：方案 3。
- **理由**：陪伴场景里情绪是有惯性的 —— 真人不会因为对方问了一句中性的话就把关切的表情收回去。
  规则只作用在**表情与语调**上，`perception.emotion_label` 仍然如实输出 `neutral`，
  所以情绪识别评测（`eval_emotion.py` 26 项）不受影响，契约字段也没变。
- **代价 / 遗留**：极端情况下（对方其实已经转好心情）会显得"还在共情"，但窗口只有 3 轮，代价很小。
  这条规则动的是**A 负责的人设表现层**，已登记在 `docs/团队任务板.md` 交接记录里，请 A 确认口径。
- **何时重新评估**：若 A 认为"该平静时就要平静"，把窗口从 3 轮改成 1 轮即可，改一处常量。

## ADR-012 · 回复长度改成「按他要什么来定」，不再一律 40 字以内

- **日期**：2026-10-24
- **背景**：真人试用时用户反馈两点：① 让它「分享一些你觉得好玩的经历」，
  回的是「糯米昨天追自己尾巴，转了好几圈撞到沙发。你小时候养过猫吗？」——
  一句话概括完立刻反问，很像敷衍；② 觉得"每次都太短"。
  原来的提示词是一条死规矩「整段回复 40 字以内」，不管对方在倾诉还是在让你讲故事，都按同一个上限压。
- **候选方案**：
  1. 全部放开，允许长回复
  2. 维持 40 字死上限
  3. 按对方的意图分档：倾诉场景保持短，被要求分享/被问日常时才允许长
- **决定**：方案 3。三档：
  | 场景 | 长度 | 依据 |
  |---|---|---|
  | 他在说自己的事（倾诉/难过/纠结） | 1–2 句，**≤40 字** | 他是主角，说多了抢他的时间 |
  | 问"你今天干嘛了""最近怎么样" | 2–3 句，**50–80 字** | 要讲一件具体小事，不能只反问 |
  | 明确让"讲讲""说说好玩的""多聊几句" | 3–5 句，**60–120 字** | 一句话概括完就反问＝没回答 |
- **理由**：「短」不是人设，是**倾听的姿态**；倾诉场景短是对的，被要求分享时短就是敷衍。
  真人不会对着一个请你讲故事的人只说一句然后反问。分档既能保住共情感，又补上了"敷衍感"。
  「分享」还额外要求讲透**一件**事（什么时候、在哪儿、发生了什么、当时怎么想），不要列三件。
- **代价 / 遗留**：长回复会让语音变长（67 字约 17 秒），演示 9 句都是倾诉场景、
  仍走短档（实测 20–37 字），演示节奏不受影响。
  这是 **A 负责的人设话术**，本次改动属用户直接要求，已登记请 A 回看口径。
- **何时重新评估**：若 A 认为某些场景该更长/更短，改 `assets/prompts/system_prompt.txt`
  的【说多长】一节即可；`experiments/eval_behavior.py` 的 `share` / `daily` 两条用例
  用 `min_len` / `max_len` 守着，改口径要同步改用例。

## ADR-013 · 音色基线抬 20Hz（微软没有中文童声，只能抬音高凑）

- **日期**：2026-10-24
- **背景**：梁苇反馈「声音有点像男生」。我先量了基频：当时线上用的（Xiaoyi + 压低 1 个半音）
  中位 **283 Hz**，落在女声/女童区间，**不可能是男声** —— 她听到的更可能是兜底语音
  （另有修复：兜底不再允许用英文男声念中文）。但用户明确要求「要符合小女孩的音色，普通话腔」。
  实测可用中文女声只有 Xiaoxiao（成人）、Xiaoyi（少女）+ 两个方言（东北/陕西），
  **没有任何真正的童声**，两个方言又与「普通话」冲突。
- **候选方案**：
  1. 换 Xiaoxiao：最暖最耐听，但一听就是成年人
  2. 换 HsiaoYu（台湾腔）：最稚嫩，但口音不是普通话
  3. 保留 Xiaoyi，**整体抬高基线音高**，让少女音更靠近童声
- **决定**：方案 3。新增 `TTS_PITCH_BASE`（默认 +20Hz），情绪的半音偏移叠在基线之上；
  难过（empathic）仍是 -1 个半音，净 +5Hz —— 既更"小"，又保留「安慰时柔下来」的对比。
- **理由**：「普通话 + 小女孩」两个条件同时满足的只有 Xiaoyi 一条路，抬音高是唯一能往前走的杠杆。
- **代价 / 遗留**：抬音高改不了共振峰（formant），抬太多会发尖失真，**20Hz 是这一轮的判断上限**，
  再高要重新试听。实测演示 9 句缓存基频中位 254–291 Hz → **314 Hz**。
  还原办法：`TTS_PITCH_BASE=0`（缓存名带实际 Hz，会自动重新生成，不复用旧音频）。
  试听对比：`experiments/voicetest/index.html`（A0 = 现在，A1 = 抬之前）。
- **何时重新评估**：若能离线部署中文童声模型（VITS / Piper 之类），直接换发音人。

## ADR-014 · 别每句都反问：一半接话、一半反问

- **日期**：2026-10-24
- **背景**：用户反馈「感觉像在面试」。为此写了 `experiments/eval_humanness.py` 量化，
  基线数据很直接：**单轮 12 条反问率 75%；连续 4 轮倾诉 反问率 100%、每轮 1.00 个问句**
  —— 也就是真实聊天里**每一句都以问号结尾**。根因是提示词规则第 2 条写死了
  「先回应他的情绪，**再问一句**」，模型只是忠实执行。
- **候选方案**：
  1. 保持现状（问句能推动对话，演示时不容易冷场）
  2. 去掉问句要求
  3. 改成「一半接话、一半反问」，并给出可执行的判断规则
- **决定**：方案 3。规则改成："**上一轮问过了，这一轮就可以不问；上一轮没问，这一轮就问一句**"；
  一轮最多问一个问题；不问时用一句陪伴性陈述收住（「嗯…我听着呢」「这事儿搁谁身上都堵得慌」）。
- **理由**：真人陪话就是这个节奏。同时用交替规则保证**话不会断**（连续两轮不问会冷场），
  比单纯"少问"更安全；演示三个场景都是倾诉，最需要这条。
- **代价 / 遗留**：第一次交互（没有历史）时仍会反问，单轮反问率 **75% → 50%**；
  真正的变化在多轮。基线是用 4 轮测的（**100%**），改后 4 轮两次分别测到 50% / 75%
  —— 4 条样本抖动太大，所以把工具扩到 **8 轮**，改后 8 轮实测 **38%**、每轮 0.38 个问句。
  ⚠️ 基线只测过 4 轮，8 轮口径没有"改前"对照，比较时以 4 轮那组为准。
  另外这轮还修掉一处内耗：`【说多长】`里倾诉那条原本还留着"挑最关键的一句回应，**再问一句**"，
  和新规则自相矛盾，已改成"问不问看情况"（这处残留是单轮反问率一直下不来的原因之一）。
  这是 A 负责的话术口径，已登记请 A 回看。
- **何时重新评估**：若观众反馈"她怎么不接话/冷场"，把交替规则放宽成"两轮至少问一次"。

## ADR-015 · 场景背景铺满整页，而不是糊在人物框后面一块

- **日期**：2026-10-24
- **背景**：C 做了「背景场景」：5 张 `bg_*.webp` + 右上角下拉 + `?bg=` 参数。
  第一版把背景图挂在 `.stage` 内部的 `.stage-bg` 上，而且沿用为"表情虚化"设计的那套
  `blur(24px) + brightness(.6)`。用户试用后一句点破：「我要的是整个页面换成那个场景，
  不是一堆黑黑的背景，你是不是把背景图放在人物框里面去了」——确实如此。
- **候选方案**：
  1. 调低模糊、提亮那块局部背景（我第一版的做法，实测还是像"糊了一块"）
  2. 场景图铺满整个视口：`body` 用 `--scene-img` cover + fixed，
     `.stage` / `.stage-card` / `.view-call` 全透明，人物画面卡加投影浮在场景上
- **决定**：方案 2。
- **理由**：虚化那层是为「同一张表情照片」服务的——它要藏住"还是那张图"，所以必须重模糊。
  真场景图的目的是**交代空间**，糊到认不出来等于没换。两种用途不该共用一套滤镜，
  更不该共用同一个挂载位置。铺满整页后观感才是"她在某个地方"，而不是"一张图里套一张图"。
- **代价 / 遗留**：
  ① 场景图上要压一层上下暗色渐变，否则顶部按钮与字幕在亮背景上读不清（已加）；
  ② **这 5 张是 picsum 随机风景图**，没有一张是"客厅/咖啡馆/书房"，与下拉文案不符 ——
     文案已改成图上真实内容（草地阳光/林间小路/湖上划船/水面倒影/山间公路）；
  ③ 素材后缀 `.webp` 实际是 JPEG，已重新编码为真 WebP；
  ④ 想要生活场景感需要 A 出图覆盖同名文件（路径与前端都不用改）。
- **建议**：情感陪伴配**自然风景**其实比"咖啡馆/书房"更稳（不会出现"咖啡馆里摆着张床"的违和）。
  若接受，就把这个功能叫「环境氛围」而不是「生活场景」。待 A 定。
- **何时重新评估**：A 出了真正的场景图后，把下拉文案改回生活场景名即可。

## ADR-016 · 桌面小人的形象：用参考图 img2img 生成 Q 版，而不是凭空文生图

- **日期**：2026-10-25
- **背景**：用户要「一打开智能体就出现的 Q 版小人」，并且要和参考视频里同一个角色。
  第一版我是纯文生图（写"Q 版可爱女孩"），结果出来的是蓝发双马尾 + 蕾丝发带 ——
  和参考图里的戴安娜（金发齐肩、白水手领配藏青滚边、藏青短裤、金色挂坠、粉色手表）
  **完全是两个人**，用户一眼就看出来了。
- **候选方案**：
  1. 继续调文生图提示词（把特征全写进去）
  2. 用参考图本身当 **img2img 输入**，只要求"改画成 Q 版风格、保留她的特征"
  3. 让 A 在豆包里出图
- **决定**：方案 2（siliconflow 的 `Qwen/Qwen-Image-Edit-2509`）。
- **理由**：文生图是"按描述重造一个人"，img2img 是"把这个人换画风"——后者天然保证同一角色。
  实测一次就拿到了对的人。**4 个表情再基于这张 Q 版底图逐张改表情**，所以 8 张帧是同一个角色。
- **代价 / 遗留**：
  ① 每张图约几分钱，8 张 + 底图共十来次调用；
  ② 生成图右下角有"AI 生成"水印 —— 水印与贴纸主体不相连，抠图时**只保留最大连通域**即可整体丢掉；
  ③ 主立绘（网页中间那张写实的灰卫衣"小雨"）**还没换**，所以同屏仍是两个形象。
     要统一就用同一套办法出 7 个写实表情替换 `assets/images/expr_*.webp`，代码不用改。
- **何时重新评估**：若 A 出图更好，直接用他的文件覆盖 `assets/pet/q_*.webp`（文件名不变，前端零改动）。
