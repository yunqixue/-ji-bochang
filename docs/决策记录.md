# 决策记录（ADR）

> 记录「为什么这么选」，避免两周后三个人都忘了原因又重新吵一遍。
> 只记**会影响多人或难以回退**的决定，小事不用写。

## 写这个文件的规则（2026-10-23 修订，起因：一次真实冲突）

1. **只追加，不改别人写的条目。** 发现别人写错了 → 在群里说，由本人改。
2. **改之前必须先 `pull`。** 不 pull 就写，几乎一定撞车。
3. **新条目追加到文件末尾**（不是最上面）。
   > 原来规定"最新的在最上面"，结果两个人同时往顶部插，git 无法自动合并，直接冲突。
   > 末尾追加虽然也可能撞，但只在"同一天两人同时写 ADR"时才会发生，概率低得多。
4. **一次只一个人写。** 三个人同一天都有决定时，商量一下谁先写，另一个等对方推完再写。
5. 写之前先看一眼文件末尾，确认最新的 ADR 编号，接着往下编。

## ADR-005 · 演示统一跑在 B 的机器上

- **日期**：2026-10-23
- **背景**：三台机器的 Python 版本不一致——A/B 是 3.10，C 是 3.14.7。C 的机器上 `uvicorn[standard]` 和 `faster-whisper` 都装不上（ADR-003），而语音识别必须跑在服务所在的那台机器上。
- **候选方案**：
  1. 三台机器都统一到 Python 3.10，谁都能起服务
  2. 演示固定跑在 B 的机器上，C 只负责静态页面文件
- **决定**：选方案 2。
- **理由**：三天内让三台机器环境完全一致成本太高；而前端页面本来就是纯静态文件，不需要 C 本机跑服务。"服务只有一台、其余人只改文件"是更省事的形态。
- **代价 / 遗留**：**单点风险**——演示机就是 B 的电脑，它出问题整个演示停摆。缓解：D3 把整机彩排 + 录屏 2 份兜底。
- **何时重新评估**：如果要让外人远程访问（C 的内网穿透任务），届时跑服务的那台就是"服务器"，这条自动成立。

## ADR-004 · 实时 TTS 少重试、演示预演多重试

- **日期**：2026-10-23
- **背景**：实测边缘情况——`edge-tts` 连微软 `speech.platform.bing.com` 在国内每次尝试成功率约 40%。如果实时对话也用 3~8 次重试，一旦网络不好，一轮对话会被拖到 **18 秒**（实测数据），演示现场不可接受。
- **候选方案**：
  1. 实时对话保持高重试次数，保证有声音
  2. 实时对话只重试 2 次，失败立刻落 Windows SAPI 离线兜底；预演时才用 8 次
- **决定**：选方案 2（`synthesize(retries=)` 参数区分两种场景）。
- **理由**：**用户等待时间的优先级高于音质**。宁可这一句用稍差的 SAPI 音色，也不能让人干等 18 秒。预演不赶时间，慢慢补到全成功。
- **代价 / 遗留**：网络差时部分回复会用 SAPI（音色差一截）；`sapi` 兜底在受限账户下可能不可用（"当前安全设置下没有可用语音"）。
- **何时重新评估**：如果换上稳定的 TTS 服务（如云端商用 TTS），重试策略可以简化。

## ADR-003 · 本机按 Python 3.14 跑，暂时不装 faster-whisper

- **日期**：2026-10-23
- **背景**：C 的机器上 Python 是 **3.14.7**（`AGENTS.md` 基线写的是 3.10）。按 `requirements.txt` 装依赖时，`uvicorn[standard]` 因为依赖 `pyyaml`（3.14 无可用轮子）直接解析失败。
- **候选方案**：
  1. 另装 Python 3.10/3.11，严格照 `requirements.txt` 装
  2. 留在 3.14，用不带 `[standard]` 的 `uvicorn`，暂时跳过 `faster-whisper`
- **决定**：先选方案 2。
- **理由**：D1 死线本来就是「装不上就降级」，先让「打字 → 听语音」能演示；环境不该卡住三个人的进度。
- **代价 / 遗留**：**ASR 不可用**（语音输入端到端是空的）；`requirements.txt` 里的 `uvicorn[standard]`、`faster-whisper` 在本机装不上，B 和 A 会踩同一个坑。已记录的替代方案：装 Python 3.11 或换云端 ASR。
- **何时重新评估**：B 决定语音输入方案时（这是感知层，归 B）。

## ADR-002 · 前端用单文件静态页，不引入构建工具

- **日期**：2026-10-23
- **背景**：仓库里没有 `src/presentation/static/index.html`，`GET /` 返回 500，整个项目没有可看的界面。
- **候选方案**：
  1. 原生 HTML/CSS/JS 单文件，FastAPI 直接托管
  2. React + Vite，构建后产物放进 `static/`
- **决定**：选方案 1。
- **理由**：零依赖零构建，演示现场断网也能开；`AGENTS.md` 明确三天内不引入新框架。接口只有 3 个，用不上框架。
- **代价 / 遗留**：页面逻辑集中在一个约 1000 行的文件里，后续改动要小心别互相踩；口型同步这类复杂交互不支持（本来也在三天排除清单里）。
- **何时重新评估**：不做，功能冻结前不再动技术选型。

## ADR-000 · 采用「三人本地 DSH + 私有 Git 仓库」协作

- **日期**：2026-__
- **背景**：三人三台电脑，都希望用 DSH 做这个项目，并且要数据共享。
- **候选方案**：
  1. 各自本地跑 DSH + 私有 Git 仓库（代码/文档共享）
  2. 一台常开机器跑 DSH Web，另两人 SSH 隧道接入（环境完全共享）
- **决定**：选方案 1。
- **理由**：DSH 是本地单用户 Agent，官方禁止 `--host 0.0.0.0`；方案 2 中所有人共享同一个系统账号和 API Key，无权限隔离且并发易冲突。方案 1 可并行、无单点、Key 不扩散。
- **代价 / 遗留**：需要各自维护环境，靠 `AGENTS.md` + 任务板保证认知一致；大数据要走云盘。
- **何时重新评估**：需要同一套重型运行环境，或必须共享同一份实时数据时再叠加方案 2。

## ADR-001 · 用 `AGENTS.md` 作为「团队大脑」

- **日期**：2026-__
- **背景**：三个 AI 实例互不相识，容易各说各的。
- **决定**：所有横向约定（分工、目录、提交规范、禁区）写进根目录 `AGENTS.md`，DSH 每次会话自动加载。
- **理由**：不需要任何额外服务，改一次全员生效，天然随仓库同步。
- **代价**：文件要短、要准；改成四人以上需拆分。
