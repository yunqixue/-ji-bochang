# 决策记录（ADR）

> 记录「为什么这么选」，避免两周后三个人都忘了原因又重新吵一遍。
> 只记**会影响多人或难以回退**的决定，小事不用写。

## 写这个文件的规则（2026-10-23 修订，起因：一次真实冲突）

1. **只追加，不改别人写的条目。** 发现别人写错了 → 在群里说，由本人改。
2. **改之前必须先 `pull`。** 不 pull 就写，几乎一定撞车。
3. **新条目追加到文件末尾**（不是最上面）。
   > 原来规定"最新的在最上面"，结果两个人同时往顶部插，git 无法自动合并，直接冲突。
   > 末尾追加虽然也可能撞，但只在"同一天两人同时写 ADR"时才会发生，概率低得多。
4. **一次只一个人写。** 三个人同一天都有决定时，商量一下谁先写，另一个等对方推完再写。
5. 写之前先看一眼文件末尾，确认最新的 ADR 编号，接着往下编。

## ADR-005 · 演示统一跑在 B 的机器上

- **日期**：2026-10-23
- **背景**：三台机器的 Python 版本不一致——A/B 是 3.10，C 是 3.14.7。C 的机器上 `uvicorn[standard]` 和 `faster-whisper` 都装不上（ADR-003），而语音识别必须跑在服务所在的那台机器上。
- **候选方案**：
  1. 三台机器都统一到 Python 3.10，谁都能起服务
  2. 演示固定跑在 B 的机器上，C 只负责静态页面文件
- **决定**：选方案 2。
- **理由**：三天内让三台机器环境完全一致成本太高；而前端页面本来就是纯静态文件，不需要 C 本机跑服务。"服务只有一台、其余人只改文件"是更省事的形态。
- **代价 / 遗留**：**单点风险**——演示机就是 B 的电脑，它出问题整个演示停摆。缓解：D3 把整机彩排 + 录屏 2 份兜底。
- **何时重新评估**：如果要让外人远程访问（C 的内网穿透任务），届时跑服务的那台就是"服务器"，这条自动成立。

## ADR-004 · 实时 TTS 少重试、演示预演多重试

- **日期**：2026-10-23
- **背景**：实测边缘情况——`edge-tts` 连微软 `speech.platform.bing.com` 在国内每次尝试成功率约 40%。如果实时对话也用 3~8 次重试，一旦网络不好，一轮对话会被拖到 **18 秒**（实测数据），演示现场不可接受。
- **候选方案**：
  1. 实时对话保持高重试次数，保证有声音
  2. 实时对话只重试 2 次，失败立刻落 Windows SAPI 离线兜底；预演时才用 8 次
- **决定**：选方案 2（`synthesize(retries=)` 参数区分两种场景）。
- **理由**：**用户等待时间的优先级高于音质**。宁可这一句用稍差的 SAPI 音色，也不能让人干等 18 秒。预演不赶时间，慢慢补到全成功。
- **代价 / 遗留**：网络差时部分回复会用 SAPI（音色差一截）；`sapi` 兜底在受限账户下可能不可用（"当前安全设置下没有可用语音"）。
- **何时重新评估**：如果换上稳定的 TTS 服务（如云端商用 TTS），重试策略可以简化。

## ADR-006 · 外网演示用 cloudflared 临时隧道，链接不写进仓库

> 编号说明：本条原写作 ADR-004（与 B 的「实时 TTS 重试策略」撞号），2026-10-23 由 B 改为 ADR-006。

- **日期**：2026-10-23
- **背景**：任务板 D2 17:00 要「队友和外人可访问的链接」，本机一个穿透工具都没装。
- **候选方案**：
  1. cloudflared quick tunnel（免注册，一条命令出 https）
  2. ngrok（要 authtoken）/ cpolar、花生壳（要账号，国内可用性好）
  3. 退化为本机 `localhost` 演示
- **决定**：用方案 1 先打通；**链接只口头/对话里发，不写进仓库、不写进文档**。
- **理由**：免注册最快能验证 A 那边能不能打开；quick tunnel 每次重启都换随机域名，写进文档第二天就是死链。
- **代价 / 遗留**：第一次建隧道超时（`api.trycloudflare.com` 连不上），重试才成功，网络不稳定；电脑休眠或进程停掉链接即失效；公网任何人都能访问，演示完必须关掉。
- **何时重新评估**：正式演示当天如果建连不稳，换国内穿透服务（cpolar / 花生壳），或按任务板降级为本机演示。

## ADR-003 · 本机按 Python 3.14 跑，暂时不装 faster-whisper

- **日期**：2026-10-23
- **背景**：C 的机器上 Python 是 **3.14.7**（`AGENTS.md` 基线写的是 3.10）。按 `requirements.txt` 装依赖时，`uvicorn[standard]` 因为依赖 `pyyaml`（3.14 无可用轮子）直接解析失败。
- **候选方案**：
  1. 另装 Python 3.10/3.11，严格照 `requirements.txt` 装
  2. 留在 3.14，用不带 `[standard]` 的 `uvicorn`，暂时跳过 `faster-whisper`
- **决定**：先选方案 2。
- **理由**：D1 死线本来就是「装不上就降级」，先让「打字 → 听语音」能演示；环境不该卡住三个人的进度。
- **代价 / 遗留**：**ASR 不可用**（语音输入端到端是空的）；`requirements.txt` 里的 `uvicorn[standard]`、`faster-whisper` 在本机装不上，B 和 A 会踩同一个坑。已记录的替代方案：装 Python 3.11 或换云端 ASR。
- **何时重新评估**：B 决定语音输入方案时（这是感知层，归 B）。

## ADR-002 · 前端用单文件静态页，不引入构建工具

- **日期**：2026-10-23
- **背景**：仓库里没有 `src/presentation/static/index.html`，`GET /` 返回 500，整个项目没有可看的界面。
- **候选方案**：
  1. 原生 HTML/CSS/JS 单文件，FastAPI 直接托管
  2. React + Vite，构建后产物放进 `static/`
- **决定**：选方案 1。
- **理由**：零依赖零构建，演示现场断网也能开；`AGENTS.md` 明确三天内不引入新框架。接口只有 3 个，用不上框架。
- **代价 / 遗留**：页面逻辑集中在一个约 1000 行的文件里，后续改动要小心别互相踩；口型同步这类复杂交互不支持（本来也在三天排除清单里）。
- **何时重新评估**：不做，功能冻结前不再动技术选型。

## ADR-000 · 采用「三人本地 DSH + 私有 Git 仓库」协作

- **日期**：2026-__
- **背景**：三人三台电脑，都希望用 DSH 做这个项目，并且要数据共享。
- **候选方案**：
  1. 各自本地跑 DSH + 私有 Git 仓库（代码/文档共享）
  2. 一台常开机器跑 DSH Web，另两人 SSH 隧道接入（环境完全共享）
- **决定**：选方案 1。
- **理由**：DSH 是本地单用户 Agent，官方禁止 `--host 0.0.0.0`；方案 2 中所有人共享同一个系统账号和 API Key，无权限隔离且并发易冲突。方案 1 可并行、无单点、Key 不扩散。
- **代价 / 遗留**：需要各自维护环境，靠 `AGENTS.md` + 任务板保证认知一致；大数据要走云盘。
- **何时重新评估**：需要同一套重型运行环境，或必须共享同一份实时数据时再叠加方案 2。

## ADR-007 · ASR 模型自管自下，不用 huggingface_hub 的缓存

- **日期**：2026-10-23
- **背景**：接通 faster-whisper 时连撞三个坑：
  ① 默认缓存目录 `C:\Users\<用户>\.cache\huggingface` 在受限账户下直接 `WinError 5` 拒绝访问；
  ② huggingface_hub 下载模型时反复卡住（几分钟才 2.5MB），无法判断是在下还是死了；
  ③ 中途断流留下的残片文件"看起来存在"（vocabulary.txt 被截到正好 256KB），
     后续报错却是 `The current model is English-only` / `token was not found in the prompt`，
     排查方向被带偏很久。
- **候选方案**：
  1. 继续用 faster-whisper 自带的 HF 下载，只改 `HF_HOME` 到项目目录
  2. 自己写下载器：urllib 直连 hf-mirror，校验 Content-Length，重试，落到 `data/models/faster-whisper-<尺寸>/`，
     代码优先加载本地目录
- **决定**：选方案 2（工具在 `experiments/download_asr_model.py`）。
- **理由**：模型 150~500MB、只在演示前准备一次，值得用最笨但可控的方式。
  长度校验是这次的关键——没有它，截断文件会伪装成"另一个完全不相关的错误"。
  本地目录还让"队友之间拷一个文件夹"成为可行的共享方式。
- **代价 / 遗留**：模型不进仓库，每台需要语音输入的机器要自己跑一次下载脚本（约 2 分钟）；
  `ASR_MODEL_SIZE` 改变后要下对应尺寸的模型。
- **何时重新评估**：如果换成云端 ASR（讯飞/阿里云），这套完全不需要了。

## ADR-008 · 通话视图用「本地自拍预览」，不做画面理解

- **日期**：2026-10-23
- **背景**：需求从「聊天框」扩到「视频通话 / 语音通话」，用户明确要「真要摄像头画面」。同时评估过 DSH 生态的四个插件（dsh-galgame / dsh-chat-avatar / dsh-plugin-quick-chat / dsh-web-ui），结论是**它们都注册在 DSH 自己的 GUI 里，装不进我们这个独立 FastAPI 页面**，只能抄设计范式。
- **候选方案**：
  1. 真 WebRTC + 视觉模型，让 AI 看懂画面
  2. 浏览器 `getUserMedia` 本地自拍预览 + 通话式界面（立绘为主、自拍小窗、通话控制条）
  3. 不做通话，只保留文字
- **决定**：选方案 2。设计参考 `dsh-galgame` 的立绘舞台 / 差分淡入 / 说话弹跳。
- **理由**：方案 1 三天内不可能（要视觉模型 + 实时推理 + 上传帧），演示现场网络也不稳；方案 2 能给出「视频通话」的完整体验感，而且摄像头画面**不出本机、不上传、不送模型**，隐私上更干净，也省掉带宽。
- **代价 / 遗留**：**她看不到你的画面**——所谓"视频通话"只有通话感和自拍预览，界面上要如实标注，别让演示时产生误解。摄像头需要 HTTPS 或 localhost 才会被浏览器授权（临时隧道是 https，可用）。无摄像头 / 被拒绝时降级为「摄像头未开」，通话界面照常。
- **何时重新评估**：要做画面理解时，需引入视觉模型 + 帧采样上送，属于下一阶段，不在三天范围内。

## ADR-009 · 效价/唤醒度交给模型直接判断，不再用后端映射表

- **日期**：2026-10-23
- **背景**：用户要求「正确读取用户的感受」。此前 `valence/arousal` 是后端按情绪标签查一张写死的映射表（sad 恒为 −0.6、happy 恒为 +0.7 等），模型只输出情绪标签，读不出同一情绪下的强度差异。
- **候选方案**：
  1. 维持映射表
  2. 让模型在 JSON 里直接输出 `valence` / `arousal`，后端只 clamp + 兜底
- **决定**：选方案 2。
- **理由**：「有点难过」和「崩溃了」不该都是 −0.6；模型本来就在生成 JSON，多两个数字成本为零，却能给更细的数值。
- **代价 / 遗留**：mock / 断网兜底仍走映射表（此时没有模型值可用）；模型给的数值要做 clamp 防越界。改动落在 B 的 `agent.py`，属用户直接要求，已登记。
- **何时重新评估**：若发现模型数值不稳定（同一句波动大），可对 valence/arousal 做滑动平滑，或退回映射表。
